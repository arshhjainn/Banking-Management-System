# Design and normalization notes

`accounts(account_id, account_number, customer_id, branch_id, account_type, balance, status)` is in 1NF: each value is atomic and rows have keys. Its main functional dependencies are `account_id -> all account attributes` and `account_number -> account_id, ...`. Customer email determines a customer (`email -> customer_id, name, phone, address`), so customer data is kept in `customers` rather than repeated per account. Branch ID determines branch name/city/address, so it is separately stored. These decompositions avoid partial/transitive dependencies (2NF/3NF) while preserving keys and allowing lossless joins on foreign keys. Email and account number unique constraints preserve alternate keys.

A multivalued dependency example: a customer may have many independent phone numbers and many independent preferences. Storing both lists in one row creates a phone × preference product; place each independent set in its own relation if that feature is added. A join dependency is a relation reconstructable from three or more projections; this small project has no justified case for a 5NF decomposition. Keep the five-table schema because these extra facts are not required here.
